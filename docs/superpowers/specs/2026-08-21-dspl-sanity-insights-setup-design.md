# DSPL Sanity Insights Setup Design

Date: 2026-08-21
Status: Approved and implemented; release gates passed 2026-08-24; ready for final review

## Objective

Connect the existing DSPL Insights publication pipeline to a new Sanity project without changing the public `/blogs` routes, editorial visual system, or static/prerendered delivery model. Editors should be able to manage articles in Sanity Studio while production builds consume only published content.

## Selected approach

Use the existing repository as the Sanity Studio workspace rather than creating a second repository or embedding Studio into the public website.

- Sanity project name: `DSPL Insights`
- Dataset: `production`
- Dataset visibility: public
- Local Studio origin: `http://localhost:3333`
- Studio configuration: existing root `sanity.config.js`
- Public delivery: build-time snapshots generated by `scripts/sync-blog-content.mjs`
- Initial content: the two approved articles in `src/cms/seedData.js`
- Hosted Studio deployment: excluded from this setup until separately approved

This approach retains one schema and one dependency tree, uses the already implemented content-sync boundary, and avoids placing Studio code or authentication inside the public React router.

## Architecture

### Authoring path

1. An authenticated editor opens Sanity Studio locally on port 3333.
2. Studio reads and writes the `production` dataset through the existing `blogPost` schema.
3. Sanity controls editor authentication. No custom DSPL admin, password store, or write API is introduced.

### Publication path

1. A site build runs `content:sync` with `SANITY_PROJECT_ID` and `SANITY_DATASET`.
2. `scripts/sync-blog-content.mjs` queries the published perspective only.
3. The sync validates required fields, allowed categories, unique safe slugs,
   strict RFC3339 dates, article bodies, and image alternative text.
4. Valid content is ordered deterministically and written to
   `src/generated/blogManifest.json` and `src/generated/blog/*.json`; the
   manifest uses deterministic `sourceUpdatedAt` provenance and never a
   wall-clock `syncedAt` field.
5. Vite prerenders the Insights index and article routes from those snapshots.

The browser-delivered application will not receive a Sanity write token. A read token remains optional and should be absent while the dataset is public.

## Configuration contract

The setup will add the missing CLI and developer-facing configuration while preserving the current schema.

- `sanity.cli.js` identifies the new project and `production` dataset for CLI commands.
- `.env.example` documents both Studio and content-sync variables.
- A local ignored `.env.local` stores the actual non-secret project identifiers for development.
- `SANITY_STUDIO_PROJECT_ID` and `SANITY_STUDIO_DATASET` configure Studio. Values with the `SANITY_STUDIO_` prefix are browser-visible and must never contain secrets.
- `SANITY_PROJECT_ID`, `SANITY_DATASET`, and `SANITY_API_VERSION` configure build-time content sync.
- `SANITY_READ_TOKEN` remains optional and undocumented as a required local value because the selected dataset is public.
- Package scripts will expose a clear Studio command and retain the explicit fallback commands.

The Sanity project ID and dataset name are identifiers, not credentials. Authentication sessions and tokens must remain outside Git.

## Initial content bootstrap

The two bundled launch articles will be converted to bootstrap records with:

- `_type: "blogPost"`
- stable `_id` values derived from the existing seed IDs
- unchanged slugs, titles, categories, publication dates, descriptions, and Portable Text bodies
- no generated or local-only metadata that Sanity owns automatically

The approved bootstrap uses the installed first-party Sanity launcher through
authenticated `sanity exec --with-user-token`. Before any mutation it calls the
direct `getDocuments(ids)` API for the two fixed IDs. The default command is a
dry-run; the explicit `npm.cmd run sanity:bootstrap -- --apply` form is the only
live form. Missing records are created in at most one transaction using only
`createIfNotExists`; when both records already exist, no transaction is
constructed or submitted. Reruns therefore cannot overwrite editor changes.

The earlier bulk-import/NDJSON path is retained only as superseded diagnostic
history; it is not the active command or architecture. No temporary import file
is used. After bootstrap, the published documents are queried and validated
against the Studio schema without printing private identifiers or revisions.

Featured illustration integration is not part of the initial import. The current local editorial illustrations remain the public listing visuals until a separately designed image-asset migration maps them into Sanity image fields and CDN delivery.

## CORS and access

The authenticated Studio needs `http://localhost:3333` as an allowed origin with credentials. No broad wildcard origin will be added. Because public content is fetched by the Node build process rather than directly from a browser, the production website does not require a credentialed CORS entry for content sync.

If Studio is later deployed, its exact hosted origin and deployment approval will be handled separately.

## Failure behavior

- Production and CI content-sync failures remain fail-closed.
- Explicit fallback commands continue to use the bundled two-article dataset.
- Local CMS development may fall back only under the current non-production behavior, with a visible warning.
- Missing identifiers, invalid content, duplicate slugs, and inaccessible datasets must produce actionable errors.
- Bootstrap must stop on authentication or validation failure, must not use
  replacement semantics, and must not submit an all-existing transaction.

## Verification

Setup is complete only when all of the following are evidenced:

1. Sanity authentication succeeds and the new project/dataset are listed.
2. Studio starts with the existing `blogPost` document type and no schema errors.
3. Exactly two initial published articles exist with the expected slugs.
4. Sanity document validation reports no schema errors for those articles.
5. A live content sync fetches both documents from Sanity rather than fallback data.
6. The generated snapshots preserve both public article routes.
7. Safe slug/path validation, deterministic `sourceUpdatedAt` provenance, and
   legacy-manifest normalization are covered by focused tests.
8. Focused content-sync tests, full tests, lint, production build, HTML
   verification, and public source-map checks pass.
9. Git inspection confirms that no authentication token, session, `.env.local`,
   generated temporary import file, or unrelated user work is staged.

## Scope boundaries

Included:

- new Sanity project and public `production` dataset
- local Studio login and operation
- CLI/project/environment configuration
- safe bootstrap of the two existing articles
- schema, sync, build, and route verification
- concise setup documentation

Excluded without separate approval:

- Studio deployment
- production hosting or DNS changes
- webhooks and automatic rebuilds
- visual editing or live preview
- image upload/migration into Sanity
- author, tag, category-document, localization, comments, or newsletter models
- changes to public Insights UI/UX
- commits, pushes, merges, or deployment
